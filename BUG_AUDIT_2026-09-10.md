### Interpreting the findings

- **High:** potential recording loss, core feature failure, memory exhaustion, or a significant release/credential boundary failure under the stated trigger.
- **Medium:** incorrect output/state, resource leaks, lifecycle races, responsiveness problems, or reliability defects.
- **Low:** a narrower usability/accessibility defect.
- **Current path:** the affected implementation is connected to app/site/tool behavior; this is not a claim that every session triggers it.
- **Conditional:** source establishes the defect, but a specific input, interleaving, device/backend, configuration, or I/O failure is needed.
- **Latent:** defective logic exists, but the relevant live path is dormant or production invocation was not established.

Severity and confidence are separate. A severe potential impact is not evidence that a device failure has been reproduced. Each entry states its evidence and limits. Suggested verification is future work, not a claim that those tests were run.

Source links are relative to this report at the repository root. Line references describe the reviewed snapshot and can move as files change.

### BUG-001 — Desktop media discovery can truncate or delete the active NPV10 master

**Severity:** High  
**Category:** Data loss / concurrency  
**Applicability:** Conditional: desktop discovery during recording

**Source:** [CamxDesktopBridgeProvider.kt:159](app/src/main/java/com/neoproc/neoproccamx/bridge/CamxDesktopBridgeProvider.kt#L159); [Npv10MasterStore.kt:162](app/src/main/java/com/neoproc/neoproccamx/recording/Npv10MasterStore.kt#L162); [Npv10FileRecovery.kt:74](app/src/main/java/com/neoproc/neoproccamx/recording/Npv10FileRecovery.kt#L74); [Npv10RecordingManager.kt:489](app/src/main/java/com/neoproc/neoproccamx/recording/Npv10RecordingManager.kt#L489).

**Mechanism.** The provider builds its catalog by constructing a fresh Npv10MasterStore and calling listMasters() without an active-file exclusion. This is a mutating recovery operation: it scans reservation-sized, unverified masters before filtering the publication list. Recovery truncates an invalid tail to the last valid frame boundary. An invalid header with the private orphan signature can instead cause deletion. A newly adopted or actively written preallocated master can satisfy these conditions.

**Trigger and impact.** An authorized desktop catalog request overlaps recording startup or a write to a reservation-sized master. The reader can mistake unwritten reservation space or an incomplete frame for abandoned data, truncate the live file, or unlink the just-created master. Subsequent writes can fail or produce an incomplete/corrupt recording. The provider's query/open/type-resolution paths share catalog resolution, increasing the number of opportunities.

**Why this is actionable.** The recording manager explicitly serializes its own scan and passes outputFile to exclude the active inode. The provider bypasses that ownership. A separate, already implemented read-only method exists: [Npv10MasterStore.kt:151](app/src/main/java/com/neoproc/neoproccamx/recording/Npv10MasterStore.kt#L151), listVerifiedMastersForPublication().

**Suggested correction.** Use verified-only, non-mutating discovery in the bridge. Keep recovery and orphan reclamation inside the recording owner's serialized lifecycle. Do not rely on a filename, age, or reservation size to distinguish an active writer.

**Verification to add.** Hold a disposable writer at preallocation, header-write, and partial-frame checkpoints; query the bridge catalog at each point. The file's inode, length, bytes, and publication state must not change as a result of discovery.

**Evidence and limits.** Confirmed call-chain defect; no destructive reproduction was performed. Access is restricted by the platform DUMP permission in [app/src/main/AndroidManifest.xml:125](app/src/main/AndroidManifest.xml#L125). This is a trusted-workflow data-safety problem, not evidence that any installed app can invoke the provider.

### BUG-002 — Object tracking interprets class-score tensors as detection records

**Severity:** High  
**Category:** Model integration / incorrect results  
**Applicability:** Current object-tracking inference path

**Source:** [AINeuralEngine.kt:891](app/src/main/java/com/neoproc/neoproccamx/ai/AINeuralEngine.kt#L891); [AINeuralEngine.kt:946](app/src/main/java/com/neoproc/neoproccamx/ai/AINeuralEngine.kt#L946); [ObjectTracker.kt:76](app/src/main/java/com/neoproc/neoproccamx/ai/ObjectTracker.kt#L76); [ObjectTracker.kt:133](app/src/main/java/com/neoproc/neoproccamx/ai/ObjectTracker.kt#L133).

**Mechanism.** The actual efficientdet_lite0.tflite asset has two FLOAT32 outputs: [1,19206,90] and [1,19206,4]. AINeuralEngine allocates only output tensor 0 and calls Interpreter.run(inputBuffer, outputArray). ObjectTracker then interprets each row as [classId, score, ymin, xmin, ymax, xmax]. Its flattening accepts the 90-value rows, so entries from the class-score vector become the supposed class identifier and box coordinates. The actual four-coordinate output is never consumed.

**Trigger and impact.** Enable object tracking and reach a successful inference with the bundled model. Detections can disappear, take incorrect classes, or produce meaningless boxes. Subject selection and any focus decisions that consume those detections become unreliable. GPU initialization failures may mask this separate parsing defect.

**Suggested correction.** Define a model-specific output adapter, request both actual output tensors, and implement the box decoding, class indexing, confidence handling, and suppression required by this exact export. Reject incompatible model signatures instead of treating any nested float array as six-value detections.

**Verification to add.** Check tensor count, shapes, types, and class mapping against the bundled bytes. Then run a labeled image fixture through the model and compare decoded boxes/classes against a trusted reference. Include empty scenes and multiple overlapping subjects.

**Evidence and limits.** Binary FlatBuffer tensor metadata was read directly; this is stronger evidence than the filename or model manifest. No model inference was executed. See the asset evidence table below for its SHA-256.

### BUG-003 — Denoise tiles consume the linear prefix of a full-HD output as a 256-square image

**Severity:** High  
**Category:** Image corruption / memory / performance  
**Applicability:** Conditional: eligible neural denoise requests up to 2.1 megapixels, with successful inference

**Source:** [AIConstants.kt:175](app/src/main/java/com/neoproc/neoproccamx/ai/AIConstants.kt#L175); [NeuralDenoiseEngine.kt:140](app/src/main/java/com/neoproc/neoproccamx/ai/NeuralDenoiseEngine.kt#L140); [NeuralDenoiseEngine.kt:406](app/src/main/java/com/neoproc/neoproccamx/ai/NeuralDenoiseEngine.kt#L406); [NeuralDenoiseEngine.kt:653](app/src/main/java/com/neoproc/neoproccamx/ai/NeuralDenoiseEngine.kt#L653); [AINeuralEngine.kt:973](app/src/main/java/com/neoproc/neoproccamx/ai/AINeuralEngine.kt#L973); [EnhancementEngine.kt:199](app/src/main/java/com/neoproc/neoproccamx/ai/EnhancementEngine.kt#L199); [NeuralDenoiseEngine.kt:75](app/src/main/java/com/neoproc/neoproccamx/ai/NeuralDenoiseEngine.kt#L75); [NeuralDenoiseEngine.kt:488](app/src/main/java/com/neoproc/neoproccamx/ai/NeuralDenoiseEngine.kt#L488); [EnhancementEngine.kt:41](app/src/main/java/com/neoproc/neoproccamx/ai/EnhancementEngine.kt#L41); [AIConstants.kt:105](app/src/main/java/com/neoproc/neoproccamx/ai/AIConstants.kt#L105).

**Mechanism.** The tile code assumes a 256 x 256 RGB model, but enhancement_denoise.tflite has fixed FLOAT32 input and output [1,1080,1920,3]. Input preparation respects the runtime tensor dimensions and resamples the tile to that size. extractFloatRgb flattens the entire output and copies the first 256 x 256 x 3 values. accumulateTile then indexes that prefix with a 256-pixel row stride.

**Trigger and impact.** The request must prefer neural processing, have at most 2,100,000 pixels, be below the severe thermal state, and have the model available. If inference succeeds, the first 65,536 pixels of a 1920-wide output are reinterpreted as a square tile; this is not a spatial resize. It corresponds to only 34 full rows plus 256 pixels of the following row. The returned enhancement can contain displaced detail, repeated strips, or severe geometry errors.

**Memory consequence.** Each tile inference produces 6,220,800 float components. The nested output representation and subsequent MutableList<Float> flattening introduce millions of small arrays/boxed values, in addition to the roughly 23.7 MiB of raw float payload. Full-frame accumulators and repeated full-HD inference amplify allocation and latency. The configured 30 ms inference budget and guided fallback can mask the image defect, but attempts that reach tensor preparation still incur the full-sized contract's cost. Exact heap use and frame time were not measured.

**Suggested correction.** Either ship the intended tile model or adapt tiling to the real model contract. Perform an explicit spatial resample when converting output sizes, validate output dimensions, and keep output in primitive contiguous buffers instead of boxing every component.

**Verification to add.** Pass a coordinate-coded RGB image through the adapter and assert that corners, rows, and tile seams remain correctly located. Measure peak heap, allocation counts, and latency with the real asset after fixing the dimensions.

**Evidence and limits.** Confirmed binary/source contract mismatch; the asset shape and SHA-256 were rechecked in pass 2. No inference or image-quality benchmark was executed. FullResolutionStillRefinementPolicy explicitly sets preferNeuralDenoise=false for its native-resolution still tiles, so this finding does not imply that every high-resolution photograph takes the neural path.

### BUG-004 — GPU interpreters are created and invoked on unrelated worker threads

**Severity:** High  
**Category:** Thread affinity / device compatibility  
**Applicability:** Conditional: GPU backend requiring thread/EGL ownership

**Source:** [AINeuralEngine.kt:298](app/src/main/java/com/neoproc/neoproccamx/ai/AINeuralEngine.kt#L298); [AINeuralEngine.kt:655](app/src/main/java/com/neoproc/neoproccamx/ai/AINeuralEngine.kt#L655); [AINeuralEngine.kt:875](app/src/main/java/com/neoproc/neoproccamx/ai/AINeuralEngine.kt#L875); [ThreadPoolManager.kt:300](app/src/main/java/com/neoproc/neoproccamx/infrastructure/threading/ThreadPoolManager.kt#L300); [AICameraPipeline.kt:498](app/src/main/java/com/neoproc/neoproccamx/pipeline/AICameraPipeline.kt#L498); [AICameraPipeline.kt:1114](app/src/main/java/com/neoproc/neoproccamx/pipeline/AICameraPipeline.kt#L1114); [DepthEstimator.kt:1043](app/src/main/java/com/neoproc/neoproccamx/ai/DepthEstimator.kt#L1043).

**Mechanism.** AINeuralEngine.loadModel constructs its GPU delegate and Interpreter on the calling thread. executeInference moves invocation to a general multiworker dispatcher. Synchronizing wrapper.lock prevents overlapping invocations but does not make execution occur on the thread/EGL context that created the delegate. The depth path has a related split: warmup can initialize DepthEstimator on the warmup executor, while estimate runs on the separate depth executor.

**Trigger and impact.** A device selects the TFLite GPU backend with thread/context ownership requirements, particularly the OpenGL path. Inference can fail with a delegate thread/context error or repeatedly fall back/degrade. A CPU-only run does not validate this path, and successful behavior on one backend does not establish safety on another.

**Suggested correction.** Give each GPU runtime a stable execution owner. Create, allocate, invoke, and close it on that owner's dedicated thread, and route warmup through the same owner. Retain serialization as well as thread affinity.

**Verification to add.** Record creation/invocation/close thread IDs in a GPU integration test; exercise warmup, first inference, repeated calls from different callers, and shutdown. Test both a relevant OpenGL GPU backend and CPU fallback.

**Evidence and limits.** The thread split is confirmed in source. Actual failure depends on the delegate/backend; no device crash or GPU failure was reproduced.

### BUG-005 — Scene-dependent YUV guessing can select the wrong range and swap valid chroma planes

**Severity:** Medium  
**Category:** Color correctness / cache identity  
**Applicability:** Current CPU YUV interpretation path

**Source:** [Yuv420ImageTools.kt:1356](app/src/main/java/com/neoproc/neoproccamx/ai/Yuv420ImageTools.kt#L1356); [Yuv420ImageTools.kt:1539](app/src/main/java/com/neoproc/neoproccamx/ai/Yuv420ImageTools.kt#L1539); [Yuv420ImageTools.kt:1609](app/src/main/java/com/neoproc/neoproccamx/ai/Yuv420ImageTools.kt#L1609); [AICameraPipeline.kt:2070](app/src/main/java/com/neoproc/neoproccamx/pipeline/AICameraPipeline.kt#L2070).

**Mechanism.** The converter scores full/limited range and normal/swapped U/V candidates using scene samples. It compares reconstructed RGB luma to the unexpanded input Y code, biasing valid limited-range black/white toward full-range interpretation. Small score differences can also select swapped chroma even though Android's YUV_420_888 planes already identify U and V. The decision is cached by dimensions/strides/buffer layout, without camera or dataspace identity.

**Trigger and impact.** A limited-range image, a colored scene that favors the wrong candidate, or a camera switch reusing the same layout can establish an incorrect cached interpretation. CPU-generated AI/proxy images can have lifted blacks, compressed whites, or reversed hues, affecting scene analysis and derived processing.

**Isolated arithmetic evidence.** With the strict-high-end scoring branch, YUV (16,128,128) gives FULL score 0 and RGB (16,16,16), while correct LIMITED black gives score 8.61 and RGB (0,0,0). YUV (235,128,128) similarly favors RGB (235,235,235) over (255,255,255). For (100,80,180), full-range unswapped scores about 3.3771 and swapped about 3.3627, so the heuristic favors the wrong hue. These are per-sample scores; a uniform sampled scene preserves the ordering.

**Suggested correction.** Use the producer's format/dataspace/range contract and documented device-specific handling. Respect plane semantics. Any unavoidable quirk cache should include producer identity and be invalidated on changes; scene appearance is not a reliable format detector.

**Verification to add.** Use deterministic limited/full-range color bars and neutral ramps, with varied strides, pixel strides, camera identities, and camera switching.

**Evidence and limits.** Source logic and isolated arithmetic were checked. This finding concerns the CPU conversion path; it does not establish that all Vulkan preview or recorded pixels use this converter.

**Category:** Native validation / compiler configuration

### LAT-003 — Two pending conversion acquires can both pass the single-active-lease check

**Severity:** Medium  
**Category:** Service lease / mutual exclusion  
**Applicability:** Latent API race; overlapping conversion callers not established

**Applicability:** Dormant custom EIS path

### LAT-006 — Direct YUV JNI reads ignore ByteBuffer position and limit

**Severity:** Medium  
**Category:** JNI buffer contract / pixel correctness  
**Applicability:** Latent direct-YUV API; current producer not established

**Source:** [AINeuralEngine.kt:1103](app/src/main/java/com/neoproc/neoproccamx/ai/AINeuralEngine.kt#L1103); [AINeuralEngine.kt:1146](app/src/main/java/com/neoproc/neoproccamx/ai/AINeuralEngine.kt#L1146); [app/src/main/cpp/ai_neural_engine_bridge.cpp:121](app/src/main/cpp/ai_neural_engine_bridge.cpp#L121).

### LAT-007 — Cache replacement retains obsolete values and corrupts memory accounting

**Severity:** Medium  
**Category:** Cache bookkeeping / retained memory / stale eviction  
**Applicability:** Latent same-key replacement API defect; sustained production replacement not established

**Source:** [MemoryCache.kt:247](app/src/main/java/com/neoproc/neoproccamx/infrastructure/cache/MemoryCache.kt#L247); [MemoryCache.kt:347](app/src/main/java/com/neoproc/neoproccamx/infrastructure/cache/MemoryCache.kt#L347); [MemoryCache.kt:384](app/src/main/java/com/neoproc/neoproccamx/infrastructure/cache/MemoryCache.kt#L384); [AINeuralEngine.kt:1126](app/src/main/java/com/neoproc/neoproccamx/ai/AINeuralEngine.kt#L1126).

**Mechanism.** put overwrites cache[key] but always adds a new CacheEntry to evictionQueue and adds its size without removing/subtracting the previous entry. The queue keeps the old value strongly reachable. Expiry/removal operates on the current map entry, so obsolete queue entries can survive even after that key expires. Later eviction polls an old entry and removes by key, which can delete a newer replacement.

**Isolated evidence and potential impact.** In a bounded translation, 100 writes of a 1,024-byte value to the same key leave one map entry, 100 queue entries, 99 obsolete retained values, and 102,400 accounted bytes for a current 1,024-byte value. With default sizeBytes=0 the memory counter cannot trigger eviction for the retained values, and map size stays one. Potential effects are retained direct/heap memory, premature eviction, and misleading cache statistics; no app heap measurement is claimed.

**Suggested correction.** Maintain map membership, eviction metadata, and byte accounting as one coordinated replacement operation. Remove/retire the exact old entry, condition eviction/removal on entry identity, and ensure cleanup also removes obsolete queue records. The related get path mutates heap comparison fields without reheapifying; recency/frequency ordering should be verified as part of the same cache-index repair rather than assumed from the PriorityBlockingQueue type.

**Verification to add.** Repeated same-key replacement, expiry after replacement, byte-accounting restoration, and stale-entry eviction must preserve only the current value. Include a get/evict recency sequence and concurrent replacement/removal with deterministic barriers.

**Reachability limit.** The live tensor-buffer caller uses a stable model/shape key under the model lock and normally reuses an existing buffer, so this review did not establish sustained same-key overwrites there. The face-embedding API also uses this cache, but no production caller of extractEmbedding was found. This is an API/data-structure defect, not a confirmed live-camera memory leak.

### LAT-008 — The LogC4 encoder and decoder fail to round-trip ordinary positive signals

**Severity:** Medium  
**Category:** Transfer-function mathematics / inverse contract  
**Applicability:** Dormant ARRI reference helpers; no current production caller found

**Source:** [AIHdrMath.kt:878](core-math/src/main/kotlin/com/neoproc/neoproccamx/ai/AIHdrMath.kt#L878); [AIHdrMath.kt:892](core-math/src/main/kotlin/com/neoproc/neoproccamx/ai/AIHdrMath.kt#L892).

**Mechanism.** arriLogC4Encode uses a linear/log branch cutoff of approximately 3.168672825 in linear input units. arriLogC4Decode chooses its branch by comparing encodedValue*28 to 64/28. These thresholds are not corresponding values of the implemented forward transform. Ordinary encoded midtones consequently enter a logarithmic inverse that produces a negative value, then are clamped to zero.

**Isolated evidence.** The source equations map linear 0.18 to approximately 0.1743547447, then decode it to 0.0. Inputs 0.1 and 0.5 also round-trip to zero; input 0.01 round-trips correctly, so a near-black-only fixture would miss the defect. This forward/inverse inconsistency is sufficient evidence without asserting an externally certified ARRI reference value.

**Suggested correction and verification.** Replace the pair with a verified, consistently normalized transfer definition and its inverse. Check reference anchors, both sides of the piecewise join, monotonicity, black handling, and round trips across the supported scene range before exposing these helpers.

**Reachability limit.** Searches found only the function definitions, with no production calls to these two helpers. The application's current LOG path uses NeoLogCurve, and tests explicitly reject obsolete ARRI shader paths. This finding does not establish that current NeoLog recordings have crushed midtones. No Kotlin or shader code was compiled or executed.
